# 数据开发技能

TRIGGER when: 用户要求进行数据仓库 SQL 开发、表结构设计、数据管道编写，或提到关键词：数据开发、SQL开发、数仓开发、写个SQL、数据管道、表结构设计、数据质量测试、DA设计

SKIP: 用户只是查询数据血缘/上下游依赖（使用 bdp-lineage skill）、查询现有 API/数据源/离线任务详情（使用 MCP 工具直接查询）、或讨论非数仓相关的通用编程问题

## 工作流

按以下阶段逐步推进，每个阶段完成后向用户确认再进入下一阶段：

### 两种工作模式

- **开发模式**：Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 4.5（可选）→ Phase 5 → Phase 6
- **审查模式**：用户直接提供 线上版本 + 变更版本 + 需求描述，从 Phase 4.5 开始执行审查

### Phase 1: 需求理解

1. 读取用户提供的设计文档/PRD/需求描述
   - 如果用户没有现成文档，引导用户填写 `templates/requirement.md`（填空式模板，7 个核心项）
2. 识别关键信息：数据来源表、筛选条件、关联逻辑、输出目标
3. **参考语义模型**：读取 `knowledge/semantic-model.json`，判断需求属于哪个业务域，参考其中的口径定义、关联关系和过滤规则
4. **自主识别歧义点并确认（先问用户，禁止自行假设）**：

   阅读需求文档时，主动发现哪里有歧义、标注了"待补充"、或者存在多种合理理解的地方。
   对有疑问的地方逐一与用户对齐，**不要机械地每次都问同样的问题**，也不要跳过明显有歧义的部分闷头写代码。

   核心原则：**需求中有歧义、待确认的部分，必须先找用户对齐，确认后再继续编写代码。不要用自己的理解代替用户的真实意图。**

5. **三条通用工作规则**：
   - **遇模糊/待补充，先问再做** — 需求文档标注"待补充"或存在多种合理理解时，不猜不填，主动确认
   - **返工成本高的决策，必须对齐** — 存储方案(加字段vs新表)、表结构设计、核心取数逻辑等一旦落地改动面广，不能闷头选
   - **Phase阶段确认，不让错误流到下一步** — 每个阶段结束前向用户确认，确保方向对了再推进，而不是写完一堆才发现基础假设错了

6. 读取源表结构：使用 MCP 工具查询需求中涉及的数据源表
   - Hive 表：`bdp_hive_table_get_detail`（传入 tblId）或 `bdp_hive_table_search`（按表名搜索）
   - MySQL 表：`bdp_mysql_get_detail` / `bdp_mysql_search`
   - MongoDB 表：`bdp_mongodb_get_detail` / `bdp_mongodb_search`
   - 离线任务：`bdp_offline_task_get_detail` / `bdp_offline_task_search`
   - 实时任务：`bdp_realtime_task_get_detail` / `bdp_realtime_task_search`
7. 核对字段名、字段类型、分区字段是否与需求文档一致，发现差异时向用户确认
8. **向用户输出需求理解摘要并确认**，确认无误后再进入下一阶段

### Phase 2: 设计方案

1. 输出设计方案草稿，包含以下核心内容：
   - 取数逻辑说明（数据来源、过滤条件、关联关系）
   - 字段映射关系（源字段 → 目标字段）
   - 上下游依赖关系
2. **向用户确认设计方案**，有异议则修改，确认后再进入下一阶段

### Phase 3: 表结构设计

1. 根据确认的设计方案生成 `CREATE TABLE` DDL
2. 字段命名：下划线小写，注释完整
3. 分区字段按业务周期确定（通常 `inc_day`，格式 `YYYYMMDD`）
4. 存储格式：`PARQUET` + 分区表

### Phase 4: SQL 开发

遵循 `docs/coding-style.md` 中的代码风格规范，核心原则：
- 关键字全小写（`select`, `from`, `where`, `join` 等）
- select 字段竖排，4空格缩进
- where 条件紧凑，≤3条件写一行
- 函数内逗号无空格：`in ('a','b')`
- join 与 on 分行
- 简单SQL用子查询 `from (select ...) alias`，不要直接 `join 表名`
- 复杂场景用 CTE `with ... as (...)`
- 更复杂需求按数仓分层设计，拆表分层

**如果语义层模型已定义该业务域**，严格参考其中的字段映射、关联条件、过滤规则、指标口径。

SQL 写完后运行校验：`python scripts/validate_sql.py <sql_file>`
- 检查项：SELECT *、分区过滤、关键字大小写、除法判空、JOIN 条件、NVL 聚合
- `--strict` 模式增加文件末尾分号检查

### Phase 4.5: 代码审查（变更验证）

当用户提供**线上版本 SQL** + **变更后版本 SQL** + **需求描述**时，执行代码审查：

1. **差异比对** — 逐行对比两个版本，识别所有变更点（新增/删除/修改的行和字段）
2. **需求覆盖度验证** — 将需求逐条拆解，检查每条需求是否在变更中体现
3. **下游影响分析** — 搜索哪些下游表/任务依赖该中间表或结果表，确认变更是否会自动传递或需要额外修改
4. **潜在问题检查** — 包括但不限于：
   - 重复项/冗余代码（如 IN 列表中重复的枚举值）
   - 遗漏场景（新增网点但未在 NOT IN 分支中排除对应岗位）
   - 字段映射一致性（case when 分支是否遗漏新增岗位的重命名逻辑）
   - 逻辑矛盾（新增条件是否与现有 where 条件冲突）
5. **输出审查报告** — 以表格形式输出：需求项 | 是否满足 | 说明，列出所有发现的问题及修复建议

审查完成后向用户确认，有问题则修复后再进入下一阶段。

### Phase 5: 数据质量测试

使用 `templates/dqc.sql` 模板生成测试用例，包含7大类测试：
1. 记录数校验（非空/唯一）
2. 枚举值与映射合法性
3. 排班状态/业务逻辑反查
4. 关键字段非空
5. 关联一致性（结果表 vs 源表）
6. 数据量波动监控（环比）
7. 边界用例（多网点/数据缺失等）

每个用例标注预期结果。

### Phase 6: 设计文档完善 + 知识沉淀

**设计文档完善** — 在 Phase 2 设计方案基础上，补充完整设计文档，包含：
需求概述、取数逻辑、映射关系、表结构、数据来源与关联、调度配置、数据质量（Phase 5 测试结果）、上下游依赖、文件清单。

**生成总报告** — 使用 `templates/report.md` 模板，生成项目交付总报告，汇总全阶段成果：
- 报告头（需求名称、执行模式、目标表、业务域）
- 源表结构确认（通过 MCP 查询结果）
- 需求理解摘要（取数逻辑、字段映射、语义层引用）
- 表结构设计（DDL 摘要）
- 核心 SQL 代码（数据流转分析、变量使用）
- 代码审查结果（仅审查模式）
- 数据质量测试（测试用例清单、覆盖度）
- 上下游依赖与调度配置
- 知识沉淀记录
- 交付物清单与执行检查清单

**知识沉淀** — 项目完成后，**主动与用户确认**是否沉淀业务知识：
- **新业务域**：生成该业务域的语义层 JSON，追加到 `knowledge/semantic-model.json`
- **新编码约定**：如果产生了不在 `docs/coding-style.md` 中的新规范，询问是否追加
- **新变量/命名约定**：询问是否更新 `AGENT.md` 中的约定

只沉淀通用规则，不做一次性决策记录。不确定时向用户提问。

## 变量约定

- 系统变量：`$[time(yyyyMMdd,-1d)]`
- 分区字段：`inc_day`
- 业务日期字段：`day`（如排班表）
