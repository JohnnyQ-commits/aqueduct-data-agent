# 数据验证 Checklist — 上线前门禁与平台坑清单

> Phase 5 强制参考。核心原则：**没在真实数据上跑过的 SQL 不算完成**。
> 临时表验证 = 用 CTAS 把变更 SQL 的产出落到 tmp 表，用真实数据证明变更正确性，通过后才允许上线。
> 没有执行通道的环境不许装"跑过"——按第〇节降级为**条件交付**，逐项标注实测状态。

## 〇、环境能力分级与降级 —— 先探测通道，再定门禁强度

> 验证门禁的价值在"实测"，但执行通道是平台相关的。本 checklist 各节按**通道无关**方式书写，执行通道按第〇节探测结果选择；各平台的通道映射（元数据/执行/编译命令示例）见 [平台通道适配映射](platform_adaptation.md)。降级改变的是"**谁来执行**"，不改变证据标准。

**第 0 步：执行通道探测**（Phase 5 开始时一次性完成）：

| 级别 | 判定 | 探测方法 |
|------|------|----------|
| **L2 全量执行** | 能提交 SQL 且能取回结果（适配器端口 / MCP / 命令行工具 / spark-submit / trino-cli 等任意实现） | `select 1` 实测一次提交+取结果 |
| **L1 仅编译** | 能触发编译/语法校验，但取数受限（权限、分区上限、无结果回传通道） | 故意提交一条语法错误 SQL，能收到编译错误 |
| **L0 无通道** | 以上均不可用（纯 LLM + 本地文件） | 命令/工具不存在即判 L0 |

**各级别产出形态**：

| 级别 | V8 编译 | V1~V7 数据验证 | 交付结论措辞 |
|------|---------|----------------|--------------|
| L2 | 实测编译 | 临时表全量实测（一~五节原样适用） | "具备上线条件" |
| L1 | 实测编译 | 产出验证 SQL 套件（哑替换规则照用），由用户平台代跑 | "编译通过；数据验证待执行" |
| L0 | 静态自检降级：语法/别名/作用域核查清单过一遍，逐段标注"未编译" | 产出**验证工具包**（SQL + 执行顺序 + 判定标准 + 占位符替换说明），用户自跑后贴回结果，agent 据实出报告 | "**条件交付（待实测）**" |

**诚实性硬规则（所有级别适用，防伪造）**：
1. 报告中每个"已验证 / 已跑通 / PASS"必须附**执行证据**（执行 ID / 结果粘贴 / 文件路径）
2. 无证据的项一律标注 `⏳ 未实测`；禁止用"应当通过""预计正常"等推断性表述冒充实测
3. L0 下不得把任何本地推演当作实测；工具包交付的报告开头必须显著声明"本报告为验证工具包，未在真实数据上执行"

## 一、验证版 SQL 生成规则

1. **基础**：取 Phase 4 正式 SQL，做两处改造：
   - **宏替换**：`$[time(...)]` 等调度宏替换为**执行当日实际值**（如 `$[time(yyyyMMdd,-1d)]` → 20260827）
   - **CTAS 化**：`insert overwrite 目标表 partition(...)` 改为 `create table 临时表 as select ...`（去掉 insert 行，select 部分原样保留）
2. **临时表命名**：`tmp_{库}.{原表名}_{YYYYMM}`（tmp 库，月份后缀）
3. **权限预检**：逐表确认个人查询身份可读（desc 或 limit 1 试探）；
   - 无权限且**属现有逻辑非本次变更点**的表 → 哑替换（空集子查询，输出 null 列），SQL 注释标明"验证用哑替换：无个人查询权限且属现有逻辑"
   - 无权限且**属本次变更点** → 必须先申请权限，不可哑替换（哑替换会掩盖变更本身的错误）
4. **IDE 单语句限制**：drop 与 create 拆成两次执行
5. 引擎选择：与生产任务一致

## 二、验证模板（V1~V8）—— 双场景基准

> **先判定场景**：**迭代需求**（已有生产表/生产 SQL 做调整）vs **全新需求**（新建表首次产出）。
> 本质区别：迭代 = **回归测试**（改的对了 + 没改的没变，锚点是生产表）；全新 = **验收测试**（从零证明产出符合业务语义，锚点是源数据 + 业务口径）。

| 验证类 | 迭代需求 | 全新需求 |
|--------|---------|---------|
| V1 结构 | 行数/主键 vs 生产表 | 行数 vs **驱动表/维度表理论行数** + 主键唯一性**首验** |
| V2 内容 | 新增字段的填充率/值域 | **全字段**首次画像 |
| V3 值正确 | 新字段 vs 源表对账 | 同左 + **抽样人工核对**（不可省） |
| V4 兼容 | 旧字段 vs 生产表 | 替换为 **DDL 对齐验证** |
| V5 容量 | 通用 | 通用 |
| V6 实测 | 通用 | 通用 |
| V7 量级 | 不需要（生产基准已锁死粒度） | **总量 vs 业务量级直觉/相关表**（粒度错误第一道防线） |
| V8 编译 | 通用 | 通用 |

### V1 结构不变性 —— JOIN 不膨胀、主键不破

**迭代**（行数 vs 生产表，证明新增 JOIN 不膨胀）：

select 'tmp' as src, count(*) as row_cnt, count(distinct 主键) as key_cnt from 临时表
union all
select 'prod' as src, count(*) as row_cnt, count(distinct 主键) as key_cnt
from 生产表 where 分区 = '当日值'

**全新**（行数 vs 驱动表理论值 + 主键首验——新表的主键从未被验证过）：

select '产出' as src, count(*) as cnt from 临时表
union all
select '驱动' as src, count(distinct 驱动键) as cnt from 驱动表 where 过滤条件
-- 主键唯一性首验
select 主键 from 临时表 group by 主键 having count(*) > 1   -- 预期 0 行

**通过标准**：产出行数 = 驱动行数；主键零重复。

### V2 内容质量 —— 填充率 / 值域 / 可解析性

- **填充率**：迭代验新增字段；全新验**全部字段**（首次画像：每列非空率、distinct 值数）
- **值域**：数值字段的合理区间（占比 [0,1]、时长 [0,24]、非负）；枚举字段合法值集合（group by 全量列出核对）
- **可解析性**：结构化字段（JSON 等）用**目标消费者同款方式**解析——后端要解 JSON，就用 JSON 解析函数验证，不能只看字符串长度
- **长度**：`max(length(字段))` vs 存储上限（如 varchar(65533)）

### V3 值正确性 —— 新字段 vs 源表对账 + 抽样人工核对

对账模板：产出字段提取值 vs 源表同款转换表达式，按关联键 left join 全量对比。
**通过标准**：100%（含空对空；源表转换表达式与产出 SQL 中的完全一致才能对平）。

**⚠️ 全新需求必须追加抽样人工核对**（迭代需求的口径正确性由生产版本背书，全新需求没有）：
- 抽 3~5 条真实记录，**人肉查源表按需求文档的口径手算一遍**，与产出对比
- 这一步验证的是**语义正确性**（口径算得对不对），对账只验证**管道正确性**（值没变形）——SQL 跑通 ≠ 口径正确
- 抽样应含正常值、边界值（极值/空值）至少各一条

### V4 向后兼容（迭代）/ DDL 对齐（全新）

**迭代**——旧字段 vs 生产表逐位置比较。
**⚠️ 非确定性字段规则**：`collect_list` / `listagg` 等聚合顺序不固定的字段，**逐位置对比会出现假差异**（两次执行顺序不同）——须**按集合对比**（sort_array + collect_set）或按计数对比。少量"顺序差异"核实集合一致即可判通过，报告中注明"固有非确定性，非变更引入"。

**全新**——DDL 对齐验证（新表特有风险：insert 列序错位）：
1. 列数与顺序核对：insert select 的列清单 vs CREATE TABLE 的列清单逐一对齐
2. 类型兼容核对：select 表达式类型 vs DDL 类型（尤其 string/数值、精度）
3. 分区字段核对：动态分区列在 select 末位且类型匹配

### V5 边界容量 —— 物理限制

新内容的最坏情况 vs 链路各环节上限（源表列、同步字段 varchar、下游解析）。

### V6 DQC 用例实测 —— 监控用例跑通才算交付

Phase 5 生成的 DQC 用例（指向生产表 + `${bizdate}`），**把表名替换为临时表、分区参数替换为实际值后在临时表上跑通**，用例才算交付。未实测的用例是设计稿，不可作为质量保障依据。

### V7 量级合理性 —— 全新需求特有（粒度错误第一道防线）

产出的总量级 vs 业务直觉 / 相关表的量级对比：
- `count(*)` 与需求方确认的业务量级对比
- distinct 主键数 vs 维度表实体数
- 单实体平均行数是否合理（如"一人一行"的表平均行数应为 1）
- 反例模式：产出"某类网点报表"跑出十几万行——实际应为该类网点几千个，全量网点类型都进了表

### V8 编译验证 —— 未执行过的新写 SQL 段，先在可执行通道上编译

**Why**：ValidatorTool 只查编码规范不解析语法，DQC 用字面日期测不到未执行段落——从未执行过的段只有目标引擎编译才能暴露语法/作用域错误（实测案例：`where` 后跟 `join` 的 ParseException；JOIN 内层子查询的列被外层跨层引用的 Invalid table alias，跨层须同层计算后透传）。

**方法（通道无关，按第〇节探测结果选择）**：宏用字面值替换后，对新增/改动的 SQL 段先编译一遍（只验证编译通过，不要求出结果）。各平台编译命令示例见 [平台通道适配映射](platform_adaptation.md) 第二节。

其他平台用等价通道（spark-submit 干跑、`EXPLAIN`、CI 语法门禁均可）；**L0 无任何通道时降级为静态自检**（对照上文两个实测案例逐段核查 where/join 顺序与跨层列引用），逐段标注"未编译"。

- 完整执行不可行时（个人无权限、IDE 单查询 400 分区上限），**编译通过即最低门槛**：报 "Error while processing statement" 阶段错误 = 语义分析已过，列引用/作用域类错误已能暴露；完整执行须走离线任务，IDE 不受限
- 方言差异勿误判：预览引擎（presto 等）与线上引擎方言不同（如 `cast(x as string)` 部分预览引擎不认），**勿因预览引擎报错误判线上 SQL 有问题**
- 适用边界：**变更管理（CR）小片段增量改动**可只编译不 CTAS 全管道（见 change-management skill Phase 4 审查维度）；首次开发的新表/新逻辑仍须走临时表完整验证（V1~V7）

## 三、平台验证坑 Checklist（按目标平台实测沉淀，初始版本如下）

| # | 坑 | 规避方法 |
|---|-----|---------|
| 1 | 查询 IDE **一次只接受一条语句**（分号多语句被解析器拒绝） | drop/create/insert 拆分多次执行 |
| 2 | bash 双引号传参时 SQL 的 **`$[0]` 被算术展开**吞掉 | 含 `$` 的 SQL 一律写文件 + `--statement "$(cat 文件)"` |
| 3 | `get_json_object` 数组索引 `'$[0].x'` 返回 null（部分 Spark 3.2 联邦引擎） | 统一用 **`'$.[0].x'`**（带点写法） |
| 4 | 子查询内 `explode(...) as 别名` 的列外层引用报 "Column not found" | 改用 **`lateral view explode(...) et as 别名`** 同层展开 |
| 5 | **presto / spark 元数据同步延迟**（新分区可能 presto 看不见） | 分区查不到时换引擎再确认，勿直接下"分区不存在"结论 |
| 6 | **个人查询身份 vs 调度身份权限差异** | 见第一节权限预检与哑替换规则 |
| 7 | Windows GBK 控制台打印中文/特殊符号崩溃 | 脚本入口 reconfigure UTF-8；或输出重定向文件 |

## 四、验证报告与临时表管理

- 产出 `Phase5-临时表数据验证报告.md`：验证项表格（含 SQL 口径说明）+ 结论（"具备上线条件"或失败项与原因）+ 环境发现
- 报告须**标明场景类型（迭代 / 全新）**及所用基准（生产表 / 驱动表 / 业务量级）
- 报告须**写明每个百分比的口径**（分母是什么、抽样还是全量），避免数字被误读
- 临时表验证后保留供业务复核，确认后 drop（写入报告备注）
- **哑替换版临时表数据不可导入生产下游正式表**——哑替换字段为空，会污染线上；仅供结构/新字段验证（平台下游链路警告见平台通道适配映射第四节）
