### 目标
将所有业务域的知识沉淀统一为**符合本体论结构**的 JSON 模型。

### 已完成的交付物
| 交付物 | 路径 | 状态 |
|--------|------|------|
| 本体论 JSON Schema | `knowledge/domains/*.json` | ✅ |
| 聚合审计文档 | `knowledge/semantic-model.md` | ✅ |
| 本体要素规范 | `skills/data-developer.md` §语义模型规范 | ✅ |
| 示例域 | `courier_compliance.json`, `rider_casual_operation.json` | ✅ |

### 本体论要素清单
每个 domain JSON 必须包含：
- **实体 (Entities)** — 含 primary_key、attributes（name/type/constraints）、source
- **层级 (Hierarchy)** — 子类划分、判别规则
- **关系 (Relationships)** — 含 cardinality（1:1/1:N/N:1/M:N）
- **度量 (Metrics)** — 含可执行 SQL 表达式
- **公理 (Axioms)** — 领域不变式，含形式化表达
- **业务规则 (Business Rules)** — 声明式约束
- **计算链路 (Computation Chains)** — 多步骤指标计算路径
- **过滤规则 (Filter Rules)** — 分区策略和过滤条件

## Phase 2: 可视化指标管理（规划中）

### 目标
基于已沉淀的本体模型，构建**可视化指标管理平台**，实现：
1. 从 `knowledge/domains/*.json` 自动生成指标目录
2. 可视化编辑指标定义、计算逻辑、预警阈值
3. 指标血缘追踪（从本体关系 + 计算链路自动生成）
4. 指标健康度监控（基于 DQC 历史结果）

### 架构设计

```
knowledge/domains/*.json
         │
         ▼
   [解析引擎]
         │
         ├──▶ 指标目录 (Web UI)
         │      - 按业务域分组
         │      - 指标卡片：名称/定义/计算式/预警阈值
         │
         ├──▶ 血缘图谱 (Mermaid / D3.js)
         │      - 实体关系 ER 图
         │      - 计算链路流程图
         │      - 指标→表→字段 三级血缘
         │
         └──▶ 健康监控 (Dashboard)
                - 指标 DQC 通过率趋势
                - 异常指标告警
                - 数据质量评分
```

### 技术选型建议

| 模块 | 建议方案 | 理由 |
|------|---------|------|
| 前端 | React + Ant Design + ECharts | 企业级组件成熟，图表丰富 |
| 解析引擎 | Python (读取 domain JSON → API) | 复用现有 Python 脚本生态 |
| API | FastAPI | 轻量、自动 Swagger 文档 |
| 存储 | domain JSON 直接作为数据源 | 避免额外数据库，单一事实源 |
| 可视化 | Mermaid（静态图）+ D3.js（交互式） | 静态图用于文档，交互图用于平台 |

## Phase 3: 反哺 Agent（规划中）

### 目标
将可视化管理平台的产出和 DQC 历史数据反哺给 Agent，形成闭环：

```
可视化平台 ──▶ 反馈数据 ──▶ Agent 知识库
     │
     ├── 指标变更 ──▶ 更新 domain JSON ──▶ Agent 下次开发自动使用新定义
     ├── DQC 失败记录 ──▶ Agent 学习常见错误模式 ──▶ Smart Fix 规则库扩展
     ├── 用户修改指标 ──▶ Agent 学习业务偏好 ──▶ 未来交付更精准
     └── 血缘图更新 ──▶ Agent 自动同步 gen_lineage.py 输出
```

### 可视化平台设计草案

knowledge/domains/*.json
         │
    [解析引擎: Python/FastAPI]
         │
         ├──▶ 指标目录 (React + Ant Design)
         ├──▶ 血缘图谱 (Mermaid 静态 + D3.js 交互)
         └──▶ 健康监控 (DQC 通过率趋势 + 告警)


### 反哺路径

| 反馈源 | Agent 受益 | 实现方式 |
|--------|-----------|---------|
| 用户在可视化平台修改的指标定义 | Agent 下次开发使用最新口径 | domain JSON 是唯一数据源，Agent 读取最新 |
| DQC 历史失败模式 | Agent Smart Fix 规则库扩展 | 从 DQC 日志提取失败模式 → 写入 `skills/data-developer.md` |
| 用户标注的"正确"血缘 | Agent 血缘解析准确率提升 | 人工校正的血线图 → 优化 gen_lineage.py |
| 指标使用频率 | Agent 优先级排序 | 高频指标优先展示、优先测试 |

### 闭环验证
- 每次 Agent 交付后，对比 domain JSON 的变更：新增实体/指标数量
- 对比 DQC 通过率趋势：Agent 是否越来越少犯错
- 对比交付工时：自动化程度是否提升

## 附录：本体论要素定义

### 为什么需要本体论结构？

1. **可计算性** — 声明式定义（公理、约束、基数）可以被机器验证，而非仅人工审查
2. **可组合性** — 实体/关系/度量独立定义，可以自由组合出新的指标
3. **可追溯性** — 每个指标都有明确的定义、来源表和计算路径，变更可追踪
4. **可验证性** — 公理是不变量，DQC 测试用例可以直接从公理生成
5. **可进化** — 新版本 domain JSON 与旧版本 diff 可精确到实体/属性/指标级别

### 本体论 vs 传统数据字典

| 维度 | 传统数据字典 | 本体论模型 |
|------|------------|-----------|
| 关注点 | "有什么字段" | "是什么、怎么关联、什么约束" |
| 关系 | 无或仅有外键 | 含基数、方向、语义描述 |
| 约束 | 无 | 声明式（NOT NULL/UNIQUE/range） |
| 不变式 | 无 | 公理（形式化表达） |
| 层级 | 无 | 子类划分、继承 |
| 可执行 | 不可执行 | 指标表达式可直接用于 SQL 生成 |
